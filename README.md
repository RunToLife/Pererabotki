# Pererabotki — «Переработка»

Веб-сервис для учета часов переработки: график дежурств (с типом дежурства, ролью и часами), график отгулов, таблицы официальных и неофициальных часов с автоматическим начислением и списанием, список дежурных и журнал аудита.

- **Стек:** Python 3.8+, Flask, SQLite, Waitress. Интерфейс — обычный HTML/JS без сборки и внешних CDN (работает без интернета, шрифты лежат в проекте).
- **Оформление:** по референсу [Approva (Kombai)](https://kombai.com/gallery/inspirations/dashboards-web-18/) — брутализм: мятный фон, жёсткие чёрные рамки со смещёнными тенями, статусы зелёный / янтарный / красный, моноширинные данные; сайдбар слева, основная панель и правая панель действий.
- **Установка:** одной командой (`install.bat` или `./install.sh`) — скрипт сам ставит всё нужное, настраивает автозапуск и запускает сервис.
- **Без интернета:** все библиотеки лежат в репозитории (`vendor/wheels`), для Windows есть встроенный Python (`vendor/python`). Установка и работа в закрытой локальной сети — см. [Установка без интернета](#установка-без-интернета).

## Быстрый старт

**Windows** — двойной щелчок по `install.bat` (или в `cmd`):

```bat
install.bat
```

**Linux / macOS:**

```bash
./install.sh
```

После установки откроется браузер на **http://127.0.0.1:8080**. Сервис запускается автоматически при каждом входе в систему.

Дальше: вкладка **«Дежурные»** → добавьте людей → вкладка **«График дежурств»** → нажмите **+** в нужном дне, выберите тип дежурства, роль и часы. В день дежурства часы сами появятся в таблице «Официальные часы» или «Неофициальные часы». Отгулы ставятся на вкладке **«График отгулов»**.

## Установка подробно

### Что делают скрипты установки

1. **Проверяют Python 3.8+.** Если его нет:
   Windows — распаковывают встроенный Python 3.12 из `vendor/python` в папку `runtime/python` (без интернета); только если архива нет — `winget`.
   Linux — `apt`/`dnf`/`pacman` (нужен доступ к репозиторию пакетов); macOS — `brew`.
   Если автоматически не получилось, скрипт скажет, что сделать вручную.
2. **Создают виртуальное окружение** `venv/` в папке проекта (системный Python не затрагивается). На Debian/Ubuntu без пакета `python3-venv` окружение создаётся без pip, а pip берётся из `vendor/wheels`.
3. **Ставят зависимости** из `requirements.txt` (Flask, Waitress) **только из папки `vendor/wheels`** (`pip --no-index`), в интернет не обращаются.
4. **Включают автозапуск** (см. таблицу).
5. **Запускают сервис** и проверяют, что он отвечает, затем открывают браузер.

| ОС | Механизм автозапуска | Когда стартует |
|---|---|---|
| Windows | Планировщик заданий, задача `Pererabotki` (без окна консоли, через `pythonw.exe`) | при входе пользователя в Windows |
| Linux | `systemd --user`, юнит `~/.config/systemd/user/pererabotki.service` | при загрузке (после `loginctl enable-linger`) / при входе |
| Linux без systemd | `cron @reboot` | при загрузке |
| macOS | `launchd`, `~/Library/LaunchAgents/ru.pererabotki.plist` | при входе пользователя |

Если на машине нет ни systemd, ни launchd, ни cron, скрипт предупредит об этом: сервис запустится сейчас, а после перезагрузки его нужно будет запускать вручную (`./start.sh`).

### Параметры установки

```bash
./install.sh --no-autostart          # только установить, без автозапуска и без запуска
PERER_PORT=9000 ./install.sh         # другой порт
```

```bat
install.bat --no-autostart
set PERER_PORT=9000 & install.bat
```

### Ручной запуск

```bash
./start.sh        # Linux / macOS
start.bat         # Windows
```

### Установка без интернета

Всё, что нужно сервису, уже лежит в репозитории, поэтому его можно ставить на компьютеры закрытой локальной сети без доступа в интернет.

| Что | Где | Для чего |
|---|---|---|
| Библиотеки Python (Flask, Waitress и их зависимости) в виде `.whl` | `vendor/wheels/` (~2 МБ) | Python 3.8–3.14; Windows x64/x86, Linux x86_64/aarch64, macOS Intel/Apple Silicon |
| `pip` 25.0.1 | `vendor/wheels/pip-25.0.1-py3-none-any.whl` | для Linux, где нет пакета `python3-venv` |
| Python 3.12.10 для Windows x64 (официальная сборка PSF, пакет `python` с nuget.org) | `vendor/python/python-3.12.10-win-amd64.zip` (~14 МБ) | если на Windows-машине Python не установлен |
| Интерфейс (HTML/JS/CSS) | `app/static/` | внешних CDN нет, браузеру интернет не нужен |

**Пошагово:**

1. На компьютере с интернетом скачайте проект: `git clone https://github.com/RunToLife/Pererabotki.git` или на GitHub **Code → Download ZIP**.
2. Перенесите папку целиком (обязательно с `vendor/`) на целевой компьютер: флешка, сетевая папка и т.п.
3. Запустите установку как обычно:
   - **Windows:** двойной щелчок по `install.bat`. Если Python не установлен, скрипт сам распакует встроенный Python в `runtime\python` (права администратора не нужны).
   - **Linux:** `./install.sh`. Нужен уже установленный Python 3.8+ — он есть в большинстве дистрибутивов (Ubuntu, Debian, Astra, РЕД ОС, ALT). Если Python нет, поставьте его с установочного диска или из локального зеркала репозитория пакетов.
4. Откройте http://127.0.0.1:8080. Чтобы сервисом пользовались другие компьютеры сети, см. [Доступ с других компьютеров](#доступ-с-других-компьютеров) — им ничего ставить не нужно, только браузер.

**Ограничения офлайн-режима:**
- Встроенный Python есть только для 64-битной Windows 8.1/10/11 (на Windows 11 ARM он работает через эмуляцию x64). На 32-битной Windows установите Python 3.8+ заранее — библиотеки для неё в `vendor/wheels` есть.
- Для Linux Python в репозиторий не кладётся: он системный и ставится средствами дистрибутива.

**Обновление набора библиотек** (для разработчика, нужен интернет): после правки `requirements.txt` выполните `vendor/update_wheels.sh` и закоммитьте папку `vendor/wheels`.

### Установка без скриптов

```bash
python3 -m venv venv
venv/bin/pip install --no-index --find-links vendor/wheels -r requirements.txt      # Windows: venv\Scripts\pip
venv/bin/python app/server.py                 # Windows: venv\Scripts\python app\server.py
```

### Обновление

```bash
git pull
./install.sh        # переустановит зависимости и перезапустит сервис
```

На Windows — `git pull`, затем `install.bat`. Перезапуск выполняется автоматически для Windows, systemd и launchd; при автозапуске через cron после обновления перезапустите сервис вручную (завершите процесс `app/server.py` и выполните `./start.sh` или перезагрузите компьютер).

База данных лежит в `data/` и при обновлении не затрагивается.

## Как пользоваться

Слева — сайдбар с шестью разделами; в его нижней части всегда видно, под какой учётной записью вы работаете и откуда взято имя (цветной бейдж: зелёный — ОС/SSO, янтарный — введено вручную, красный — не определено). Справа от основной таблицы или календаря — панель действий: форма добавления и сводка.

Цвета бейджей: **зелёный** — официальные часы и создание записи, **янтарный** — неофициальные часы и изменение, **красный** — удаление.

### График дежурств

- Календарь текущего месяца (неделя с понедельника, выходные подсвечены, сегодня выделен).
- **+** в ячейке дня — назначить дежурного. В форме:
  - **Дежурный** — из списка дежурных;
  - **Тип дежурства** — Официальное или Неофициальное (по умолчанию Официальное);
  - **Роль** — Дежурный, Помощник дежурного, Смена или Иное (по умолчанию Дежурный);
  - **Часы** — сколько часов начислить (по умолчанию **24**, от 0,25 до 24);
  - **Примечание** — необязательно, например «ночная смена».

  В один день можно назначить нескольких, но одного человека — только один раз.
- Плашка в календаре: ФИО, роль (Деж. / Пом. / Смена / Иное) и часы. **Зелёная** — официальное дежурство, **жёлтая** — неофициальное. **✓** — часы за дежурство уже начислены.
- **Нажмите на плашку**, чтобы изменить тип, роль, часы или примечание. Если часы уже начислены, запись в таблице часов обновится автоматически (при смене типа — переедет в другую таблицу).
- **×** на плашке — снять дежурного с этого дня. Если часы уже были начислены, они удаляются из таблицы (сервис предупредит).
- Справа — сколько дежурств и сколько официальных/неофициальных часов по графику у каждого сотрудника за месяц.
- **Прошлые месяцы:** кнопки **‹ ›**, поле выбора месяца или список «Месяцы с данными…». Прошлые месяцы можно и редактировать — все правки попадают в аудит.

### График отгулов

Отдельный календарь, устроен так же, как график дежурств.

- **+** в ячейке дня — поставить отгул. В форме:
  - **Сотрудник**;
  - **Списать часы из** — «Официальные часы» или «Неофициальные часы» (по умолчанию Официальные);
  - **Часы** — сколько списать (по умолчанию **8**, от 0,25 до 24);
  - **Примечание** — необязательно.
- Часы **сразу списываются** из выбранной таблицы: там появляется запись «Отгул» с отрицательными часами (например, −8) на дату отгула.
- Если после списания остаток станет меньше нуля, сервис спросит подтверждение (поставить можно, например, если часы будут отработаны позже).
- **Нажмите на плашку**, чтобы изменить тип часов, количество или примечание — списание пересчитается. **×** — отменить отгул, часы вернутся.
- Справа — **«Остаток часов»** по каждому сотруднику за всё время: начислено минус списано, отдельно по официальным и неофициальным часам.
- Одному сотруднику на один день — один отгул.

### Официальные часы / Неофициальные часы

Две независимые таблицы с одинаковым интерфейсом. Записи в них появляются тремя способами:

| Основание | Откуда | Часы | Можно ли править в таблице |
|---|---|---|---|
| **Дежурство** | Автоматически в день дежурства, по типу дежурства | `+24` (или сколько указано) | Нет — правится в графике дежурств |
| **Отгул** | Автоматически при постановке отгула, по выбранному типу часов | `−8` (или сколько указано) | Нет — правится в графике отгулов |
| **Вручную** | Форма «Новая запись» справа | `+` | Да: «Изменить», «Удалить» |

В колонке «Тип дежурства / комментарий» у автоматических записей указано, например, «Официальное дежурство · Дежурный · 24 ч» или «Отгул · списано 8 ч». Итог за месяц — начислено минус списано. В колонке «Внёс» у автоначислений стоит «система».

Ручной ввод:

- Панель **«Новая запись»** справа: дата, сотрудник, часы (от 0,25 до 24, шаг 0,25), комментарий → **Добавить**.
- Под полями формы — **проверки в реальном времени** (✓ — в порядке, ! — предупреждение, ✕ — ошибка): допустимы ли часы, выбран ли сотрудник, попадает ли дата в выбранный месяц и **дежурит ли сотрудник в этот день по графику**. Предупреждения не блокируют добавление (например, переработка может быть и вне графика дежурств); блокирует только сервер при некорректных данных.
- В таблице: **Изменить** и **Удалить** для ручных записей, видно, кто внёс запись; у автоматических вместо кнопок — пометка «авто». Строка «Итого за месяц» — внизу, сумма также в бейдже в заголовке карточки.
- При правке записи удалённого сотрудника он остаётся выбранным (с пометкой «удалён») — запись не «переедет» на другого человека.
- Блок **«Сводка по сотрудникам»** показывает за месяц официальные, неофициальные и общую сумму часов по каждому человеку.

### Дежурные

- Форма «Добавить дежурного»: ФИО и должность (оба поля обязательны). Дубликаты по ФИО (без учёта регистра) не принимаются.
- **Изменить** — правка ФИО и должности.
- **Удалить** — человек пропадает из списков и выпадающих меню. Что происходит при удалении:
  - **будущие** дежурства и отгулы (после сегодняшнего дня) снимаются, каждое снятие записывается в аудит; списанные за будущие отгулы часы возвращаются;
  - **прошлые и сегодняшние** дежурства, отгулы и все часы **сохраняются**, ФИО остаётся в истории и отчётах;
  - запись в базе помечается как неактивная, а не стирается.

### Аудит

Журнал всех изменений. Для каждого события хранится:

- **Когда** — дата и время;
- **Кто** — учётная запись и IP-адрес;
- **Действие** — создание / изменение / удаление;
- **Где** — раздел (Список дежурных, График дежурств, График отгулов, Официальные часы, Неофициальные часы);
- **Что и на что** — текстовое описание и поля «было → стало» (для изменений — только изменившиеся поля).

Что попадает в аудит после этого обновления дополнительно:

- назначение, изменение (тип, роль, часы, примечание) и снятие дежурства;
- **автоначисление** часов за дежурство — автор «система», в описании тип дежурства, роль и `+часы`;
- постановка, изменение и отмена отгула, а также **списание** часов (`−часы`) и их возврат;
- перенос автоматической записи из одной таблицы часов в другую при смене типа.

Фильтры: по разделу, по автору (например, «система»), по тексту описания.

### Как работает автоначисление и списание

**Начисление за дежурство** происходит, когда наступает день дежурства (по часам сервера):

1. **При запуске сервиса** — начисляются все дежурства, день которых уже наступил (например, если компьютер был выключен).
2. **Периодически** — фоновая проверка раз в 5 минут (настраивается `PERER_ACCRUE_INTERVAL`), поэтому часы появляются вскоре после полуночи даже без действий пользователей.
3. **При каждом обращении к сервису** — та же проверка, чтобы открывший страницу сразу видел начисление.
4. Если дежурство назначено **на сегодня или задним числом**, часы начисляются сразу.

Каждое дежурство начисляется **ровно один раз**: у дежурства ставится отметка «начислено», поэтому повторные проверки, перезапуски и одновременные запросы часы не задваивают. Будущие дежурства не начисляются, пока не наступит их день.

**Списание за отгул** происходит сразу при постановке отгула (запись датируется днём отгула). Отмена отгула возвращает часы, изменение — пересчитывает.

**Обновление со старой версии.** При первом запуске новой версии база дополняется новыми полями автоматически. Уже назначенным дежурствам присваивается тип «Официальное», роль «Дежурный» и 24 часа. Дежурства, день которых **уже наступил до обновления**, задним числом **не начисляются** (часы за них могли внести вручную) — при необходимости поправьте тип у будущих дежурств, нажав на плашку. Журнал подгружается по 50 записей («Показать ещё»). Изменить или удалить записи аудита через интерфейс или API нельзя.

## Как определяется имя пользователя

### Почему раньше имя показывалось неправильно

Браузер сам по себе не сообщает сайту, под какой учётной записью Windows вошёл человек. В первой версии сервис брал имя так: если страницу открыли **на самом сервере**, подставлялась учётная запись, под которой запущен процесс сервиса (`getpass.getuser()`), а всех остальных просил ввести имя вручную. Из‑за этого:

- при подключении с другого компьютера показывалось `unknown@<IP>` или то, что человек ввёл сам (могло быть что угодно);
- если сервис стоит на общем/терминальном сервере, всем, кто открыл его на этом сервере, показывалась учётка того, кто запустил сервис;
- имя было без домена (`ivanov` вместо `CORP\ivanov`) и без ФИО;
- если сервис запущен через обратный прокси, все запросы приходили с `127.0.0.1` и получали учётку сервера.

### Как работает сейчас: вход по учётной записи Windows / Active Directory

Получить имя пользователя от Windows **можно** — тем же способом, что используют SharePoint, IIS и внутренние порталы: **встроенная проверка подлинности Windows** (Integrated Windows Authentication, протоколы **NTLM** и **Kerberos**, HTTP‑схема *Negotiate*). Браузер сам, без ввода пароля, доказывает серверу, кто вошёл в Windows, а сервер проверяет это средствами самой Windows.

```
браузер                                    сервер "Переработка" (Windows)
  │ GET /api/login/windows                     │
  │ ─────────────────────────────────────────► │
  │ 401  WWW-Authenticate: NTLM                │
  │ ◄───────────────────────────────────────── │
  │ Authorization: NTLM <запрос>  (тот же TCP) │
  │ ─────────────────────────────────────────► │ ─► SSPI AcceptSecurityContext
  │ 401  WWW-Authenticate: NTLM <вызов>        │
  │ ◄───────────────────────────────────────── │
  │ Authorization: NTLM <ответ>                │
  │ ─────────────────────────────────────────► │ ─► Windows/контроллер домена проверяет ответ
  │ 200  {login: "CORP\ivanov",                │ ─► имя: QueryContextAttributes(NAMES)
  │       display: "Иванов Иван Иванович"}     │ ─► ФИО из AD: TranslateName
  │ + cookie сессии (подписана, 12 часов)      │
```

Как это устроено в коде:

- **`app/winauth.py`** — обращается к системной библиотеке Windows `secur32.dll` (SSPI) через стандартный модуль `ctypes`. **Новых библиотек ставить не нужно**, поэтому офлайн‑установка продолжает работать. Пароль пользователя сервис не видит и не хранит: токены проверяет Windows (при доменной учётке — вместе с контроллером домена).
  - `SspiAuthenticator.step()` — один шаг рукопожатия (`AcceptSecurityContext`). Незавершённые рукопожатия NTLM хранятся по ключу «IP:порт клиента», потому что NTLM требует, чтобы все шаги шли по одному TCP‑соединению (Waitress держит keep‑alive). Брошенные рукопожатия удаляются через 2 минуты.
  - После успешного входа имя берётся из контекста безопасности (`QueryContextAttributes(SECPKG_ATTR_NAMES)`) в виде `ДОМЕН\логин`, а ФИО — из Active Directory (`TranslateName` → `NameDisplay`). Если ФИО получить нельзя (компьютер не в домене), показывается только логин.
  - `process_user()` — для подключений с самого сервера: учётка процесса сервиса тоже с доменом и ФИО (`GetUserNameEx`).
- **`app/server.py`**
  - `GET /api/login/windows` — точка входа: отвечает `401` с заголовком `WWW-Authenticate`, принимает токены браузера, после успеха записывает `ДОМЕН\логин` и ФИО в подписанную cookie сессии (`perer_session`, ключ подписи создаётся в `data/secret.key`). Дальше рукопожатие не повторяется 12 часов.
  - `POST /api/logout` — сбросить вход.
  - Во всех записях аудита автор пишется как `Иванов Иван Иванович (CORP\ivanov)`; фильтр «Кто изменил» ищет и по ФИО, и по логину.
  - Режим `PERER_AUTH=windows` + `PERER_ALLOW_MANUAL=0`: пользователь без подтверждённой учётки может только смотреть, любые изменения отклоняются с кодом 401.
- **`app/static/app.js`** — при открытии страницы, если пользователь ещё не определён, интерфейс один раз сам вызывает `/api/login/windows`; в сайдбаре показывается ФИО, под ним логин и бейдж «вход Windows / AD». Если автоматически не получилось, есть кнопка **«Войти через Windows»** (браузер спросит логин и пароль домена) и, если разрешено, ручной ввод имени.
- **`settings.env`** — файл настроек в корне проекта; читается при запуске, так что режим можно поменять без переустановки (переменные окружения важнее файла).

### Порядок определения пользователя

| № | Условие | Источник имени | Бейдж |
|---|---|---|---|
| 1 | Человек уже вошёл через Windows (есть cookie сессии) | `ДОМЕН\логин` + ФИО из AD | вход Windows / AD |
| 2 | `PERER_AUTH=proxy` и пришёл заголовок `X-Remote-User` (или `REMOTE_USER`) | Имя от обратного прокси с SSO | SSO через прокси |
| 3 | Подключение с самого сервера (`127.0.0.1`/`::1`), режимы `auto` и `off` | Учётка, под которой запущен сервис, с доменом и ФИО | учётная запись ОС |
| 4 | Ничего из выше; ручной ввод разрешён и имя введено | Имя, введённое вручную (cookie) | введено вручную |
| 5 | Ничего из перечисленного | `unknown@<IP>`; интерфейс пробует вход Windows, затем просит имя | не определено |

### Режимы (`PERER_AUTH`)

| Режим | Когда использовать |
|---|---|
| `auto` (по умолчанию) | Сервис на Windows, коллеги заходят по сети. Сетевые пользователи входят по учётке Windows/AD, на самом сервере — учётка сервиса. |
| `windows` | Строгий режим для домена или терминального сервера: **все**, включая открывших сервис на самом сервере, входят только по своей учётке Windows; ручной ввод выключен. |
| `proxy` | Перед сервисом стоит IIS/Apache/nginx, который сам проверяет пользователя (SSO) и передаёт имя в `X-Remote-User`. Включайте, только если до порта сервиса нельзя достучаться в обход прокси. |
| `off` | Без входа Windows (Linux/macOS или отладка): учётка сервиса на localhost и ручной ввод. |

На Linux и macOS вход Windows недоступен (нет SSPI) — режимы `auto`/`windows` там ведут себя как `off`. Для домена на Linux используйте режим `proxy` с Apache `mod_auth_gssapi` или nginx `spnego-http-auth`.

### Пошаговая настройка в домене Active Directory

1. **Сервер.** Компьютер, где стоит сервис, должен быть в домене (иначе вход по доменным учёткам не пройдёт и ФИО не найдутся). Установите сервис с доступом из сети:
   ```bat
   set PERER_HOST=0.0.0.0 & install.bat
   ```
   Для строгого режима раскомментируйте в `settings.env` строку `PERER_AUTH=windows` и перезапустите сервис.
2. **Брандмауэр.** Откройте порт (от имени администратора):
   ```bat
   netsh advfirewall firewall add rule name="Pererabotki" dir=in action=allow protocol=TCP localport=8080
   ```
3. **Адрес для пользователей.** Заходите по **короткому имени** сервера без точек: `http://srv-duty:8080`. Такие адреса Windows сама относит к зоне «Местная интрасеть», и Edge/Chrome/IE передают учётку **без запроса пароля**. По IP‑адресу (`http://10.0.0.5:8080`) или полному имени (`srv-duty.corp.local`) браузер по умолчанию спросит логин и пароль — вход всё равно сработает, но не автоматически.
4. **Если нужен адрес с точками или IP** — добавьте его в зону интрасети групповой политикой (администратор домена):
   - *Конфигурация пользователя → Административные шаблоны → Компоненты Windows → Internet Explorer → Панель управления браузером → Вкладка «Безопасность» → Список назначений зоны для веб-сайтов*: `http://srv-duty.corp.local` = `1` (Местная интрасеть). Это действует на Edge и Chrome.
   - Либо политика Chrome/Edge `AuthServerAllowlist` = `srv-duty.corp.local`.
   - **Firefox**: `about:config` → `network.automatic-ntlm-auth.trusted-uris` (и для Kerberos `network.negotiate-auth.trusted-uris`) = `srv-duty.corp.local`, или те же параметры политикой `Authentication`.
5. **Проверка.** Откройте сервис с рабочей станции: в сайдбаре должно быть ваше ФИО, под ним `CORP\логин` и зелёный бейдж «вход Windows / AD». В `data\server.log` появится строка `Вход по учетной записи Windows: CORP\логин (ФИО)`.

### Kerberos (необязательно)

По умолчанию сервис предлагает браузеру **NTLM**: он работает под любой учётной записью без настройки домена. Kerberos надёжнее и быстрее, но требует SPN — без него браузер получит билет, который сервис не сможет расшифровать, и вход не пройдёт. Чтобы включить Kerberos:

1. Зарегистрируйте SPN на учётке, под которой работает сервис (при установке через `install.bat` это учётка пользователя, вошедшего на сервер):
   ```bat
   setspn -S HTTP/srv-duty CORP\svc-duty
   setspn -S HTTP/srv-duty.corp.local CORP\svc-duty
   ```
   Если сервис запущен от имени `SYSTEM`/`NETWORK SERVICE`, SPN не нужен: подходит учётка компьютера.
2. В `settings.env`: `PERER_KERBEROS=1`, перезапустите сервис.

Если в домене NTLM запрещён политикой, Kerberos — единственный вариант.

### Если вход Windows не работает

| Симптом | Причина и решение |
|---|---|
| Браузер спрашивает логин и пароль | Адрес не в зоне «Местная интрасеть» — см. шаги 3–4. Можно ввести `CORP\логин` и пароль домена, вход тоже пройдёт. |
| «Windows отклонила вход» | Включён `PERER_KERBEROS=1`, а SPN не настроен — уберите настройку или зарегистрируйте SPN. Либо сервер не в домене и не доверяет учётке. |
| Вместо ФИО только `CORP\логин` | Серверу не удалось прочитать AD (не в домене или нет связи с контроллером). На вход не влияет. |
| Бейдж «учётная запись ОС» показывает не того человека | Сервис открыт на самом сервере в режиме `auto` — показывается учётка процесса. Для общего/терминального сервера включите `PERER_AUTH=windows`. |
| Вход срабатывает через раз | Между браузером и сервисом стоит прокси, разрывающий соединения (NTLM требует одного TCP‑соединения). Ходите напрямую или используйте режим `proxy`. |

### Безопасность

- Пароли через сервис не проходят и нигде не хранятся.
- Cookie сессии подписана ключом из `data/secret.key`: подделать имя нельзя. Удаление файла разлогинит всех.
- Заголовок `X-Remote-User` игнорируется во всех режимах, кроме `proxy`, — иначе любой мог бы подставить чужое имя.
- Ручной ввод имени всегда помечается в аудите бейджем «введено вручную»; в домене его лучше выключить (`PERER_ALLOW_MANUAL=0`).
- Трафик идёт по HTTP. NTLM/Kerberos не передают пароль, но cookie сессии можно перехватить в сети. Для повышенных требований поставьте перед сервисом HTTPS‑прокси.

## Доступ с других компьютеров

По умолчанию сервис слушает только `127.0.0.1` — то есть доступен только на том компьютере, где запущен. Чтобы открыть его для коллег:

1. Установите с `PERER_HOST=0.0.0.0` (Windows: `set PERER_HOST=0.0.0.0 & install.bat`).
2. Откройте порт в брандмауэре.
3. Коллеги заходят на `http://<адрес-сервера>:8080`.

**Безопасность.** В сервисе нет паролей и ролей: любой, кто достучался до порта, может читать и менять данные. Открывайте доступ только во внутренней сети, а для надёжной идентификации в аудите используйте SSO через прокси (см. [выше](#как-определяется-имя-пользователя)). Для доступа из интернета нужен HTTPS-прокси с аутентификацией.

## HTTP API

Все ответы — JSON. Ошибки: `{"error": "текст"}` с кодом 4xx.

| Метод и путь | Назначение |
|---|---|
| `GET /api/me` | Текущий пользователь: `{user, login, display, source, windows_auth, allow_manual, auth_mode}` |
| `POST /api/me` | Задать имя вручную: `{name}` (403, если ручной ввод выключен) |
| `GET /api/login/windows` | Вход по учётной записи Windows/AD (HTTP NTLM/Negotiate, отвечает 401 до завершения рукопожатия) |
| `POST /api/logout` | Сбросить вход |
| `GET /api/employees[?all=1]` | Список дежурных (`all=1` — включая удалённых) |
| `POST /api/employees` | Добавить: `{full_name, position}` |
| `PUT /api/employees/<id>` | Изменить: `{full_name, position}` |
| `DELETE /api/employees/<id>` | Удалить (мягко, снимает будущие дежурства) |
| `GET /api/duties?month=ГГГГ-ММ` | Дежурства за месяц (с `kind`, `hours`, `role`, `accrued_at`) |
| `POST /api/duties` | Назначить: `{date, employee_id, kind, hours, role, note}`; по умолчанию `kind=official`, `hours=24`, `role=duty` |
| `PUT /api/duties/<id>` | Изменить: `{kind, hours, role, note}` (начисленные часы пересчитываются) |
| `DELETE /api/duties/<id>` | Снять дежурство (начисленные часы удаляются) |
| `GET /api/dayoffs?month=ГГГГ-ММ` | Отгулы за месяц |
| `POST /api/dayoffs` | Поставить отгул: `{date, employee_id, kind, hours, note}`; по умолчанию `kind=official`, `hours=8` |
| `PUT /api/dayoffs/<id>` | Изменить: `{kind, hours, note}` (списание пересчитывается) |
| `DELETE /api/dayoffs/<id>` | Отменить отгул (часы возвращаются) |
| `GET /api/balance` | Остаток часов за всё время по каждому сотруднику: `{official, unofficial}` |
| `GET /api/hours/<kind>?month=ГГГГ-ММ[&employee_id=N]` | Часы за месяц; `kind` = `official` или `unofficial`; поле `source` = `duty` / `dayoff` / `manual` |
| `POST /api/hours/<kind>` | Добавить: `{date, employee_id, hours, comment}` |
| `PUT /api/hours/<kind>/<id>` | Изменить (те же поля); только ручные записи, для автоматических — 409 |
| `DELETE /api/hours/<kind>/<id>` | Удалить; только ручные записи, для автоматических — 409 |
| `GET /api/hours/summary?month=ГГГГ-ММ` | Сводка по сотрудникам: официальные / неофициальные / всего |
| `GET /api/months` | Месяцы, за которые есть данные |
| `GET /api/audit?entity=&actor=&q=&limit=&offset=` | Журнал аудита (новые сверху) |

Даты — `ГГГГ-ММ-ДД`. Часы — число больше 0 и не больше 24. Тип: `official` / `unofficial`. Роль: `duty` (Дежурный), `assistant` (Помощник дежурного), `shift` (Смена), `other` (Иное).

### Вход по учётной записи Windows / Active Directory (2026-10-06)

**Что изменилось для пользователя**
- Исправлено неверное имя пользователя. Коллеги, открывающие сервис по сети, входят по своей учётной записи Windows (NTLM, по желанию Kerberos) **без ввода пароля**; в сайдбаре показываются ФИО из Active Directory, под ним `ДОМЕН\логин` и бейдж «вход Windows / AD». В аудит автор пишется как `Иванов Иван Иванович (CORP\ivanov)`. Подробно — [Как определяется имя пользователя](#как-определяется-имя-пользователя).

**Технически**

- `app/server.py`: `GET /api/login/windows` (рукопожатие NTLM/Negotiate, ключ соединения «IP:порт»), `POST /api/logout`, подписанная cookie сессии (`data/secret.key`, 12 часов); настройки `PERER_AUTH` (`auto`/`windows`/`proxy`/`off`), `PERER_ALLOW_MANUAL`, `PERER_KERBEROS`; `PERER_TRUST_PROXY=1` по-прежнему работает (= `PERER_AUTH=proxy`); чтение `settings.env` при запуске.

- Тестов стало 27 (было 21): рукопожатие в 2 шага на имитации SSPI, отказ при смене соединения, выход, режимы `windows` и `off`, распознавание первого токена.

## Известные ограничения

- Нет паролей и разграничения прав (см. [Доступ с других компьютеров](#доступ-с-других-компьютеров)).
- Автоматический вход по учётке Windows работает, только когда сервис запущен на Windows; на Linux/macOS — через SSO‑прокси (режим `proxy`).
- Нет выгрузки в Excel/PDF и итоговых отчётов за период длиннее месяца.
- Ручные записи часов не привязаны к дежурствам: форма лишь предупреждает, если сотрудник в этот день по графику не дежурит, но запись разрешает.
- День дежурства определяется по дате и часам компьютера, на котором работает сервис; время начала смены не учитывается (начисление — с 00:00 дня дежурства).
- Остаток часов может уйти в минус: при постановке такого отгула сервис только предупреждает.
- Записи аудита нельзя удалить через сервис, но тот, у кого есть доступ к файлу `data/pererabotki.db`, может изменить его напрямую.
